# Contributing to Ragging Reporting Mobile App

We love your input! We want to make contributing to this project as easy and transparent as possible, whether it's:

- Reporting a bug
- Discussing the current state of the code
- Submitting a fix
- Proposing new features
- Becoming a maintainer

## Development Process

We use GitHub to host code, track issues and feature requests, and accept pull requests.

## Pull Requests

Pull requests are the best way to propose changes to the codebase. We actively welcome your pull requests:

1. Fork the repo and create your branch from `main`.
2. If you've added code that should be tested, add tests.
3. If you've changed APIs, update the documentation.
4. Ensure the test suite passes.
5. Make sure your code lints.
6. Issue that pull request!

## Any contributions you make will be under the MIT Software License

In short, when you submit code changes, your submissions are understood to be under the same [MIT License](http://choosealicense.com/licenses/mit/) that covers the project. Feel free to contact the maintainers if that's a concern.

## Report bugs using GitHub's [issue tracker](https://github.com/RensithUdara/ragging_reporting_mobile_app/issues)

We use GitHub issues to track public bugs. Report a bug by [opening a new issue](https://github.com/RensithUdara/ragging_reporting_mobile_app/issues/new); it's that easy!

## Write bug reports with detail, background, and sample code

**Great Bug Reports** tend to have:

- A quick summary and/or background
- Steps to reproduce
  - Be specific!
  - Give sample code if you can
- What you expected would happen
- What actually happens
- Notes (possibly including why you think this might be happening, or stuff you tried that didn't work)

## Code Style Guidelines

### Flutter/Dart Guidelines
- Follow the [Dart Style Guide](https://dart.dev/guides/language/effective-dart/style)
- Use `flutter format` to format your code
- Use meaningful variable and function names
- Add comments for complex logic
- Keep functions small and focused

### File Organization
- Place files in appropriate directories according to MVC architecture
- Use lowercase with underscores for file names (e.g., `user_model.dart`)
- Import statements should be organized:
  1. Flutter imports
  2. Package imports
  3. Project imports

### Commit Messages
- Use clear and meaningful commit messages
- Start with a verb in the imperative mood (Add, Fix, Update, Remove)
- Keep the first line under 72 characters
- Add more details in the body if necessary

Example:
```
Add user authentication validation

- Validate email format
- Check password strength requirements
- Add proper error messages
```

## Testing Guidelines

- Write unit tests for business logic
- Write widget tests for UI components
- Write integration tests for user flows
- Aim for good test coverage
- Mock external dependencies

## Code Review Process

1. All submissions require review before merging
2. Reviewers will check:
   - Code style and formatting
   - Test coverage
   - Documentation updates
   - Performance implications
   - Security considerations

## Feature Requests

We encourage feature requests! Please:

1. Check if the feature already exists or is planned
2. Provide detailed description of the feature
3. Explain the use case and benefits
4. Consider the impact on existing functionality
